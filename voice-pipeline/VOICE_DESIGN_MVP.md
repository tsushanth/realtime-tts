# voice-design-dev: Parler-TTS direct-serve MVP

Status: v1 prototype, deployed under `voice-design-dev` on Modal (**not** `voice-intake`/`voice-train`,
**not** production). Not wired into any product surface.

## What this is

A "voice design" v1: submit a natural-language voice **description** ("a calm, warm female voice
with a slight British accent...") plus a line of **text**, and get back a WAV generated by
[Parler-TTS](https://github.com/huggingface/parler-tts) (`parler-tts/parler-tts-mini-v1`), an
open-weights model that conditions generation directly on a text description - no per-voice
training, no fine-tune, no export. This is deliberately the smallest possible "hear a voice
concept" loop, not a Piper-style trained/deployed custom voice. Runs on Modal, scale-to-zero GPU
(A10G), same pattern as `voice-train.py`'s `train_voice` (spawn-and-poll, GPU function separate
from the always-warm-enough web function).

## API

Bearer `VOICE_DESIGN_SECRET` (Modal secret `voice-design-dev`), same auth shape as `intake.py`.

```
POST /designs             {description, text} -> {job_id, status: "queued"}
GET  /designs/{job_id}    -> {status: queued|running|ready|failed, ...timings on ready}
GET  /designs/{job_id}/audio  -> wav bytes (409 until status == ready)
```

Validation: `description` must be 10-800 chars, `text` must be 1-500 chars, both required and
non-empty; missing/short/oversized values get a 400 before anything is queued. Same "roll back the
enqueued state and 503 if spawn fails" pattern as `intake.py`'s `ingest_zip`.

Deploy: `modal deploy voice_design_dev.py`. Secret must hold `VOICE_DESIGN_SECRET` (create with
`modal secret create voice-design-dev VOICE_DESIGN_SECRET=<random>`).

## Measured latency and cost (real runs on 2026-09-21, this session)

Two independent end-to-end cold-start generations were run against the deployed app (not
simulated/estimated):

| Run | description | text | model load | generation | audio produced | total wall time (submit -> ready) |
|---|---|---|---|---|---|---|
| 1 | "calm, warm female voice, slight British accent, professional customer-service tone" | "Thanks for calling..." (52 chars) | 26.85 s | 4.91 s | 2.97 s | ~39 s |
| 2 | "deep, gravelly male voice, slow and deliberate, noir detective narrator" | "The rain never stopped..." (44 chars) | 32.96 s | 8.17 s | 3.73 s | ~63 s |

Both runs were cold starts (`scaledown_window=60`, and in practice the container was gone well
before the next request in both cases) - **there is no measured warm-request number yet**; every
real request in this MVP today pays model load. Model load dominates total latency (69-52% of wall
time) and is mostly downloading/initializing the ~880M-parameter Parler-TTS-mini weights plus CUDA
context, not generation itself.

Generation time is NOT strictly proportional to output audio length in these two samples (4.91s
generate -> 2.97s audio vs. 8.17s generate -> 3.73s audio); two data points is not enough to fit a
real-time-factor number, only to say it lands somewhere around 2-2.5x real time on an A10G once the
model is loaded, for short (1-2 sentence) prompts. This needs more runs before quoting an RTF with
confidence.

**Cost** (measured GPU-seconds x Modal's published A10G on-demand rate, $1.10/GPU-hour = $0.0003056/s;
this is the public rate, not pulled from a billing API - actual invoiced amount should be confirmed
against the Modal dashboard before this number is used for pricing decisions):

- Run 1: 26.85 + 4.91 = 31.76 GPU-seconds -> **~$0.0097** (~1 cent)
- Run 2: 32.96 + 8.17 = 41.13 GPU-seconds -> **~$0.0126** (~1.3 cents)

At this cold-start-dominated rate, cost per generation is roughly **1-1.5 cents**, almost entirely
model-load overhead rather than inference. A warm/kept-alive container would cut this by ~70-80%
per call (down to roughly the generation-only cost, ~$0.0015-0.0025), at the expense of paying for
idle GPU time between requests - a real tradeoff this MVP does not make a decision on.

Compare to the existing pricing note in project memory (~$0.044/min realtime voice cost, $0.10/min
billed): this MVP's cost is per-generation (a few seconds of audio), not per-minute, and is not
currently comparable to a production per-minute figure - it should not be treated as a proxy for
what a shipped voice-design feature would cost without a warm-pool/throughput analysis.

## What's left before shipping (not done here)

- **No warm-path / RTF benchmark** - only 2 cold-start data points; need a batch of runs (varied
  description length, varied text length) to get real p50/p95 latency and a trustworthy
  generation-time-vs-audio-length curve.
- **No description quality/adherence evaluation** - nothing here checks whether the generated voice
  actually matches the requested description (Parler-TTS's conditioning is probabilistic; some
  descriptions steer better than others). That's a real product question, unaddressed.
- **No rate limiting / per-key quotas** - auth is a single shared secret exactly like `intake.py`'s
  bearer-token pattern; there's no per-caller throttling, so this is not safe to expose broadly as-is.
  Existing `voice-intake`'s API-key layer is the pattern to reuse (see `VOICE_API_DRAFT.md`), not
  built here.
- **No job cleanup / TTL** - `/jobs` volume grows unbounded; production would need to delete old
  job dirs (audio + status.json) after some retention window (`voice-intake`/`voice-train`'s
  180-day retention note in project memory would be the reference).
- **No persistent voice identity** - unlike the Piper flow, there is no `voice_id` you can reuse;
  every `/designs` call is a one-off generation from a text description, so "designing a voice" and
  reusing it later is not yet a concept this API has. Adding a saved-description "preset" would be
  a small addition on top of this if wanted.
- **Not integrated with the gateway/backend auth (API keys, Supabase users)** - this uses a single
  Modal-secret bearer token like `intake.py`, appropriate for a dev prototype but not for exposing
  outside this Modal account.
- Generation quality by ear has not been assessed here - only that the pipeline runs end-to-end and
  produces valid WAV audio; no listening evaluation was performed.

## Cleanup / production-safety confirmation

- App name is `voice-design-dev`, distinct from `voice-intake`/`voice-train`; nothing under those
  production names was touched or redeployed.
- Volume `voice-design-dev-jobs` and secret `voice-design-dev` are new and dev-scoped; existing
  `voice-datasets`/`voice-models`/`voice-intake` volumes and secrets were not modified.
- `scaledown_window=60` is set on the GPU function; `modal app list` was checked after each test run
  and confirmed 0 running tasks (scaled to zero) before moving on.
- No push to any git remote; all work is local commits on the `voice-design-mvp` branch in this
  worktree.

## Known operational note from this session

While testing, the `voice-design-dev` app briefly showed as `stopped` in `modal app list` between
two of the test calls, and a queued job never progressed - most likely another concurrent
session/agent on the same Modal account touched the app (several other apps also churned through
create/stop cycles during this window, e.g. `voice-conve...` apps unrelated to this work). Redeploying
(`modal deploy voice_design_dev.py`) brought it back immediately and the next request completed
normally. Anyone re-running these tests on a shared Modal account should expect this kind of
cross-session interference and treat a stuck "queued" job as a signal to check `modal app list`.
